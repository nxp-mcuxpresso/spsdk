------
AHAB
------

AHAB (Advanced High Assurance Boot) is the container format and secure boot mechanism of devices with a dedicated
security subsystem: the Security Controller (SECO) on i.MX 8QM/8QXP/8DXL, or EdgeLock Enclave (ELE) / EdgeLock Secure
Enclave on i.MX 8ULP, i.MX 9x and i.MX RT118x. Older devices
such as i.MX RT10xx and RT115x/RT116x/RT117x use :doc:`/images/hab` instead; see the :doc:`/devices_list` for the features supported by each
device. A configuration file in YAML or JSON is used to instruct nxpimage how the output should look like.


Example of use for export
``nxpimage ahab export -c "path\to\config\file.yaml"``

Example of use for parse binary AHAB container
``nxpimage ahab parse -b "my_ahab_container.bin" -o "path\to_parsed_data"``

The full AHAB configuration template could be generated by nxpimage tool "get_template" sub-command for family that supports AHAB, example:
``nxpimage ahab get-template -f rt118x -o ahab_template_rt118x.yaml``

Image placement and application linking
=======================================

AHAB configuration describes the payload layout, not the application's linker settings.
SPSDK does not inspect application linking or infer execute-in-place (XIP) placement from
``load_address`` or ``entry_point``. The user is responsible for keeping these addresses,
the linked application and the final programmed image consistent.

For target memories other than ``serial_downloader``, a nonzero ``image_offset`` explicitly
sets the payload position within the AHAB image. An omitted or zero offset uses sequential
placement with the existing alignment rules. The first automatically placed payload starts
after the container reservation, using the device database's ``start_image_address`` when
defined, or the container-version default otherwise. RT266x already defines ``0x9000``.
In ``serial_downloader`` mode, explicit offsets are ignored and images are placed automatically.

Bootable image handles placement of the AHAB image on the boot medium. For example, the
RT266x XSPI NOR layout places AHAB at flash offset ``0x1000``. If flash is mapped at
``0x60000000`` and an application must execute at ``0x60030000``, the user must configure
``image_offset: 0x2F000`` relative to AHAB. Neither AHAB nor bootable image derives this
value from the load address or validates it against the application's actual linking.
The generic AHAB ``standard`` target does not imply a particular flash interface or XIP mode.

Generating Multiple Bootable Image Templates
=============================================

For families that support IMX bootloaders (like i.MX 8/9 series), you can generate multiple template configurations using the ``get-templates`` command:

``nxpimage bootable-image get-templates -f <family> -o <output_directory>``

This command generates:
- Standard templates for all memory types
- Extra templates with simplified naming (e.g., ``spl`` for primary image, ``uboot`` for secondary image)
- Board-specific template variants in sub-folders

To generate a specific template type:

``nxpimage bootable-image get-templates -f <family> -o <output_directory> --template imx_boot_flash_all``

To generate templates for a specific board:

``nxpimage bootable-image get-templates -f <family> -o <output_directory> --board imx95-19x19-lpddr5-evk``

Use ``nxpimage bootable-image list-boards -f <family>`` to see available boards.

AHAB Extensions
================
Since SPSDK version 2.2.0, support for AHAB extensions have been added.
This allows the user to create the standard images like U-Boot for example in the similar manner as with the imx-mkimage tool, without knowing the details of the AHAB format.

AHAB Sign
==========
Since SPSDK version 2.3.0 it is possible to sign and encrypt existing image or image container set, without parsing.

It parses the input image, loads the configuration file and iterates over the segments in the image. If the segment is AHAB image, it iterates over all the containers and if the container is not NXP signed,
it signs them with the key (signature provider) provided in the configuration.

If the blob is specified, it also iterates over all images in the container and encrypt them.

Then signed (encrypted) image is saved to the path provided.

Template for signing might be generated using the get-template command with --sign/-s flag:
``nxpimage ahab get-template -f <family> -o sign_template.yaml --sign``

Example of use for sign and encrypt AHAB container
``nxpimage -v ahab sign -c "path\to\config\file.yaml" -b "ahab_image_to_be_signed.bin" -o "path\to_signed_image"``

For an example of signing an existing image, including one built by the i.MX Linux Yocto BSP,
see :doc:`Signing an existing image </examples/ahab/imx95/imx95_ahab_sign>`. For building
containers from individual binaries, see `Mapping Yocto BSP Output Files to SPSDK Inputs`_.

AHAB Re-sign
============
It is possible to re-sign an existing AHAB container without modifying other parts of the image. This is useful when you need to update the signature of a specific container without rebuilding the entire image.

The re-sign command allows you to specify a private key or signature provider configuration to sign a specific container in the AHAB image.

Example of use for re-signing a container in an AHAB image:
``nxpimage ahab re-sign -f <family> -b "ahab_image.bin" -k "path/to/private_key.pem" -i <container_id>``

For bootable images that contain FCB or XMCD segments, you need to specify the memory type:
``nxpimage ahab re-sign -f <family> -b "bootable_image.bin" -k "path/to/private_key.pem" -i <container_id> -m <memory_type>``

AHAB Update Keyblob
===================
It is possible to update the encryption keyblob in an existing AHAB container. This is useful when you need to update the encryption keys without rebuilding the entire image.

The update-keyblob command allows you to replace the keyblob in a specific container of an AHAB image with a new one.

Example of use for updating a keyblob in an AHAB image:
``nxpimage ahab update-keyblob -f <family> -b "ahab_image.bin" -k "path/to/new_keyblob.bin" -i <container_id>``

For bootable images that contain FCB or XMCD segments, you need to specify the memory type:
``nxpimage ahab update-keyblob -f <family> -b "bootable_image.bin" -k "path/to/new_keyblob.bin" -i <container_id> -m <memory_type>``


AHAB Container Structure for imx-boot (i.MX 9x)
==================================================

On i.MX 9x devices (i.MX93, i.MX95, etc.), the ``imx-boot`` image is composed of multiple AHAB containers,
each carrying different firmware and application images. The boot ROM processes these containers sequentially.

Understanding this structure is essential when creating or modifying bootable images with SPSDK.

Common Structure
-----------------

All i.MX 9x families share a two-stage boot concept:

1. **Primary Container Set** — loaded first by boot ROM to on-chip SRAM (OCRAM)
2. **Secondary Container Set** — loaded to DDR after memory initialization

.. list-table:: Generic imx-boot Container Layout
   :header-rows: 1
   :widths: 15 30 20 35

   * - Container
     - Contents
     - Signed By
     - Purpose
   * - Container 0
     - ELE firmware
     - NXP
     - EdgeLock Enclave security subsystem; loaded and verified first by ROM
   * - Container 1
     - SPL + DDR firmware (LPDDR FW or OEI)
     - OEM
     - Initializes DDR memory and hands off to U-Boot
   * - Container 2
     - ATF (BL31) + U-Boot proper (+ optional OP-TEE)
     - OEM
     - Main bootloader loaded into DDR

i.MX93 Container Layout
-------------------------

The i.MX93 uses AHAB Container v1. DDR initialization uses legacy LPDDR training firmware
(4 separate binaries merged with SPL into a single ``spl_ddr`` image), **not** OEI.

.. list-table:: i.MX93 imx-boot Structure
   :header-rows: 1
   :widths: 15 35 50

   * - Container
     - Contents
     - Notes
   * - Container 0 (NXP)
     - ELE firmware (``mx93a1-ahab-container.img``)
     - NXP-signed; mandatory; processed first by ROM
   * - Container 1 (OEM, OCRAM)
     - | ``spl_ddr`` — U-Boot SPL
       | ``lpddr_imem_1d`` — LPDDR4 instruction memory 1D
       | ``lpddr_dmem_1d`` — LPDDR4 data memory 1D
       | ``lpddr_imem_2d`` — LPDDR4 instruction memory 2D
       | ``lpddr_dmem_2d`` — LPDDR4 data memory 2D
     - | Loaded to OCRAM; SPL initializes DDR
       | SPL + LPDDR FW are merged into single image
   * - Container 2 (OEM, DDR)
     - | ``atf`` — ATF / BL31
       | ``uboot`` — U-Boot proper
       | ``tee`` — OP-TEE (optional)
       | Optional: ``kernel``, ``dtb``
     - Loaded to DDR after initialization

**Supported cores**: Cortex-A55, Cortex-M33, ELE, V2X_1, V2X_2

i.MX95 Container Layout
-------------------------

The i.MX95 has a more complex structure, supporting both AHAB Container v1 (a0/a1) and v2 (b0+),
and adds System Manager, OEI-based DDR initialization, and Fast Boot capabilities.

.. list-table:: i.MX95 imx-boot Structure
   :header-rows: 1
   :widths: 15 35 50

   * - Container
     - Contents
     - Notes
   * - Container 0 (NXP)
     - ELE firmware (``mx95b0-ahab-container.img``)
     - NXP-signed; mandatory; processed first by ROM
   * - Container 1 (OEM, OCRAM)
     - | ``oei_ddr`` — OEI DDR firmware
       | ``lpddr_imem`` — LPDDR4/5 instruction memory
       | ``lpddr_dmem`` — LPDDR4/5 data memory
       | ``lpddr_imem_qb`` — LPDDR4/5 instruction memory (Quick Boot)
       | ``lpddr_dmem_qb`` — LPDDR4/5 data memory (Quick Boot)
       | ``system_manager`` — System Manager (CM33)
       | ``cortex_m7_app`` — M7 application (optional)
       | ``spl`` — U-Boot SPL
       | ``v2x_dummy`` — V2X dummy image
     - | System Manager runs on dedicated CM33 core
       | QB data is optional (dummy variant available on b0)
       | OEI TCM (``oei_tcm``) available as extra image
   * - Container 2 (OEM, DDR)
     - | ``atf`` — ATF / BL31
       | ``uboot`` — U-Boot proper
       | ``tee`` — OP-TEE (optional)
       | Optional: ``kernel``, ``dtb``
     - Loaded to DDR after initialization

**Supported cores**: Cortex-A55, Cortex-M33, Cortex-M7, ELE, V2X_1, V2X_2, DDR

Mapping Yocto BSP Output Files to SPSDK Inputs
-------------------------------------------------

Most users obtain the binaries listed above from an i.MX Linux (Yocto) BSP build. The Yocto
build places them in its deploy directory ``tmp/deploy/images/<machine>/``; the boot firmware
used by ``imx-mkimage`` is collected in the ``imx-boot-tools/`` sub-directory. There are two
common scenarios:

1. **Signing an already-built image** — Yocto already produced a complete bootable image
   (``imx-boot-<machine>-<boot device>.bin-<target>``, e.g.
   ``imx-boot-imx93-11x11-lpddr4x-evk-sd.bin-flash_singleboot``). No component mapping is
   needed; pass this file as the ``-b`` input of ``nxpimage ahab sign``
   (see `AHAB Sign`_ and the :doc:`/examples/ahab/imx95/imx95_ahab_sign` example).

   .. note::

       Signing succeeds regardless of how U-Boot was built, but the chain of trust is complete
       only if U-Boot (SPL and U-Boot proper) was built with ``CONFIG_AHAB_BOOT=y``. Without it,
       the boot ROM still authenticates the containers it loads (ELE firmware and the SPL
       container), but SPL loads the container with ATF, U-Boot and OP-TEE without
       authentication, and U-Boot does not authenticate the images it loads later (e.g. the
       kernel). The device then boots even if these images are modified, also in
       the OEM closed lifecycle. The default i.MX Linux BSP does not enable this option.

2. **Building the container set with SPSDK** — the individual components are needed.
   ``nxpimage bootable-image get-templates`` generates configurations that already use
   the Yocto default file names for the selected board, so you only need to copy the files
   from the Yocto deploy directory into the generated ``inputs`` folder::

       nxpimage bootable-image list-boards -f mimx9596
       nxpimage bootable-image get-templates -f mimx9596 -o imx95_templates --template imx_boot_flash_all --board imx95-15x15-lpddr4x-evk

The table below lists the inputs used by the templates and where they come from. Exact names
(e.g. the DDR firmware version suffix or the ``<machine>`` name) depend on the device, board
and BSP release; ``nxpimage bootable-image list-boards -f <family>`` shows the names used for
each supported board.

.. list-table:: Yocto BSP output -> SPSDK AHAB inputs
   :header-rows: 1
   :widths: 15 20 35 30

   * - Container
     - SPSDK input
     - Yocto file name (example)
     - Note
   * - Container 0 (NXP)
     - ELE firmware
     - ``mx93a1-ahab-container.img``, ``mx95b0-ahab-container.img``
     - YAML key: ``binary_container`` (``path``); NXP-signed
   * - Container 1 (OEM, OCRAM)
     - LPDDR training firmware
     - ``lpddr4_imem_1d_v202201.bin``, ``lpddr5_dmem_v202409.bin``, ...
     - --
   * -
     - OEI DDR firmware
     - ``oei-m33-ddr.bin``
     - i.MX 94/95 only
   * -
     - OEI TCM firmware (optional)
     - ``oei-m33-tcm.bin``
     - | TCM initialization (ECC configuration etc.)
       | i.MX95 A1 only; not used on B0
   * -
     - System Manager
     - ``m33_image-mx95evk.bin``
     - YAML key: ``system_manager`` (i.MX 94/95 only)
   * -
     - Cortex-M7 application (optional)
     - ``imx95-19x19-evk_m7_TCM_power_mode_switch.bin``
     - i.MX 95 only
   * -
     - U-Boot SPL
     - ``u-boot-spl.bin`` or ``u-boot-spl.bin-<machine>-<boot device>``
     - | YAML key on i.MX93: ``spl_ddr``
       | For AHAB boot, U-Boot must be compiled with ``CONFIG_AHAB_BOOT=y`` and ``CONFIG_CONSOLE_MUX=y``
   * - Container 2 (OEM, DDR)
     - ARM Trusted Firmware
     - ``bl31-imx93.bin``, ``bl31-imx95.bin``; ``bl31-<soc>.bin-optee`` when OP-TEE is enabled
     - YAML key: ``atf``
   * -
     - U-Boot proper
     - ``u-boot.bin`` or ``u-boot-<machine>.bin-<boot device>``
     - For AHAB boot, U-Boot must be compiled with ``CONFIG_AHAB_BOOT=y`` and ``CONFIG_CONSOLE_MUX=y``
   * -
     - OP-TEE (optional)
     - ``tee.bin``
     - --

.. warning::

    The default i.MX Linux BSP builds U-Boot **without** ``CONFIG_AHAB_BOOT``, so U-Boot does
    not authenticate the images it loads. For secure boot, enable ``CONFIG_AHAB_BOOT=y`` in the
    U-Boot configuration and rebuild before signing.

The FRDM board is not listed in ``nxpimage bootable-image list-boards``. Use the
``imx95-15x15-lpddr4x-evk`` board templates and adjust the file names that differ:
``cortex_m7_app`` (``imx95-15x15-frdm_m7_TCM_power_mode_switch.bin``) and ``atf``
(``bl31-imx95.bin-optee`` when OP-TEE is enabled).

In ``imx-boot-tools/``, the System Manager image ``m33_image-mx95evk.bin`` keeps ``evk`` in its
name also for FRDM boards, because the FRDM machine configuration reuses the i.MX 95 EVK System
Manager configuration (``mx95evk``). It is the correct image for the FRDM board and can be used
as it is.

.. note::

    Refer to the `i.MX Linux Site <https://www.nxp.com/design/design-center/software/embedded-software/i-mx-software/embedded-linux-for-i-mx-applications-processors:IMXLINUX>`_
    for more information.

i.MX 95 Container Parameters
-------------------------------

The following container header fields are relevant when building AHAB images for
**i.MX 95** (``AHABContainerV2``). They control the GDET (Glitch Detector) runtime
behavior and the fast boot hardware-acceleration mode.

.. note::

   Both ``gdet_runtime_behavior`` and ``fast_boot`` are **optional** in the OEM
   container YAML. When a field is omitted, SPSDK preserves the flag bits already
   present in the parsed container (e.g., from the NXP-signed ELE firmware container)
   rather than overwriting them with a default. Set either field explicitly only when
   you want to override the value that was read from the original image.

GDET Runtime Behavior
^^^^^^^^^^^^^^^^^^^^^^

The ``gdet_runtime_behavior`` field controls the Glitch Detector (GDET) managed by
the EdgeLock Secure Enclave (ELE) during and after container authentication.

.. list-table:: GDET runtime behavior options
   :header-rows: 1
   :widths: 30 70

   * - Value
     - Description
   * - ``disabled`` *(default)*
     - GDET is disabled after the first OEM container has been authenticated.
   * - ``enabled_eleapi``
     - GDET is automatically enabled during all ELE API calls.
   * - ``enabled``
     - GDET remains enabled after container authentication.

Example YAML snippet::

    containers:
      - container:
          gdet_runtime_behavior: disabled   # or enabled_eleapi / enabled

Fast Boot (V2X Accelerator)
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

The ``fast_boot`` field enables hardware-accelerated authentication using the V2X
subsystem of i.MX 95 (B0 revision and later). It corresponds to bits [17:16] in the
32-bit container header Flags field. This acceleration can dramatically reduce boot
time — e.g., Linux kernel verification was measured at ~2671 ms in normal mode
vs ~445 ms with fast hash (on an i.MX 95 LPDDR5 EVK).

.. list-table:: Fast boot options
   :header-rows: 1
   :widths: 40 60

   * - Value
     - Description
   * - ``disabled`` *(default)*
     - Regular secure boot, no V2X acceleration (bits 16:17 = ``0b00``).
   * - ``hash_and_copy``
     - ELE performs hash and copy instead of BootROM (bit 16 only, ``0b01``).
   * - ``external_accelerator``
     - **Fast Hash** — V2X handles container/image authentication. Works with
       all boot sources including SD and eMMC (bit 17 only, ``0b10``).
   * - ``hash_and_copy_with_external_accelerator``
     - **Full Fast Boot** — ELE does hash + copy using V2X accelerator directly.
       Requires boot from **FlexSPI NOR flash**. Maximum performance
       (bits 16:17 = ``0b11``).

.. note::

   Full Fast Boot (``hash_and_copy_with_external_accelerator``) additionally
   requires the ``FAST_BOOT_ENABLE`` hardware fuse to be programmed
   (bit 4 of fuse word 58, fuse index 1860 on i.MX 95).
   Fast Hash (``external_accelerator``) also requires the fuse to be programmed.
   The fuse enables the feature globally; the container header selects the mode.
   See the *Fast Boot with V2X Accelerator on i.MX 95* application note for details.

.. note::

   The V2X subsystem on i.MX 95 B0 operates in **direct mode** for fast boot:
   no V2X firmware is running during the fast boot phase, and the ELE controls
   the V2X hardware accelerators directly. After fast boot completes, V2X
   firmware is downloaded and executed normally.

.. note::

   On i.MX 95 B0, i.MX 943 and i.MX 952, both Fast Hash and Full Fast Boot rely on
   the V2X (Prime) firmware. The boot ROM requires:

   - the V2X (Prime) container in the NXP container set (``binary_container``),
   - the ``v2x_dummy`` image entry in the OEM container that uses fast boot,
   - no double authentication (the ELE/V2X containers can't be packaged as OEM images).

   If any of these is missing, the ROM boot flow fails and moves to the next boot
   stage. The ``hash_and_copy`` value alone (``0b01``) is an invalid setting on these
   devices and causes the container authentication to fail. SPSDK reports a warning
   during the image verification in these cases.

Example YAML snippet::

    containers:
      - container:
          fast_boot: disabled            # or hash_and_copy / external_accelerator /
                                         # hash_and_copy_with_external_accelerator
          gdet_runtime_behavior: disabled
